# Contributing to RhinoAI

Thanks for taking a look. This file covers how to get a change from your machine into `main`.

## Before you start

- **Bug fixes and small improvements:** open a PR directly. Link the issue if one exists.
- **New tools, new model adapters, protocol changes, or anything that touches the router/plug-in contract:** open an issue first so we can agree on the shape before you write it.
- **Questions:** the [AI category on the McNeel forum](https://discourse.mcneel.com/c/rhino/artificial-intelligence-rhino/162) is the fastest place to get an answer.

## Setup

See [Requirements](README.md#requirements) and [Quick start](README.md#quick-start) in the root README. Run `git lfs pull` after cloning; `.png`, `.3dm`, `.gh`, and `.ghz` files are stored in LFS.

## Making a change

1. Fork and branch from `main`. Name the branch `<you>/<topic>`.
2. Keep the change scoped. One component per PR is easiest to review.
3. Add or update tests in the matching project under [`tests/`](tests).
4. Run the checks for what you touched (below).
5. Open a PR against `main` with a short description of what changed and why. Screenshots or a `.3dm`/`.gh` file help for anything visible in Rhino.

## Checks by component

| You changed | Run |
|---|---|
| `rhino/router` | `dotnet test tests/Router.Tests -c Release` |
| `rhino/plugin/Server` or tools | `dotnet test tests/Server.Tests -c Release` |
| `rhino/sdk` | `dotnet test tests/sdk.tests -c Release -p:ExposeInternalsToTests=true` |
| `rhino/panel` | `npm run typecheck && npm test && npm run verify` (in `rhino/panel`) |
| `shared/router-launcher.mjs` | `node --test` (in `tests/launcher`) |
| `connector` | `npx @anthropic-ai/mcpb validate manifest.json && node build.mjs` |
| Router ↔ plug-in behavior | `dotnet test tests/Integration.Tests` (needs Rhino; not run in CI) |

Release builds use `TreatWarningsAsErrors`. Build with `-c Release` once before pushing.

## Conventions

### `.ai.cs` files

Any C# file drafted by an AI coding agent is named `<Name>.ai.cs`. The suffix records provenance so reviewers know where to look harder. Hand-written files keep their names when edited. Full rules in [AGENTS.md](AGENTS.md).

If you add a `.ai.cs` file that `tests/Server.Tests` links in by path, update the explicit `<Compile Include>` list in that csproj.

### Code style

- Follow [`.editorconfig`](.editorconfig).
- C# 12, nullable enabled. `ImplicitUsings` is off in the plug-in.
- The plug-in targets both `net8.0` and `net48` on Windows. Don't use APIs that break the `net48` build without a polyfill.
- No logging to stdout in the router. Stdout is the JSON-RPC channel.

### Duplicated files

- `cc-plugin/router-launcher.mjs` is a committed copy of `shared/router-launcher.mjs`. A test checks they are byte-equal, so edit `shared/` and copy.
- `rhino/acp/src/Generated/` is generated by `rhino/acp/codegen`. Don't hand-edit it.
- `rhino/acp/schema/` is vendored from upstream ACP. See `SOURCE.md` before updating.

### Versioning

Don't bump `RhinoAIPackageVersion` in your PR. Maintainers set it when cutting a release on `rhino-9.x`.

## Adding an MCP tool

1. Add a static class under `rhino/plugin/Tools/` marked `[McpServerToolType]`.
2. Add a method marked `[McpServerTool("snake_case_name", "Title", readOnly, destructive)]` with a `[Description]`. Parameters get `[Description]` too; `RhinoDoc` is injected.
3. Return an `IToolResult`. Use `Failure(ToolError.…)` for expected failures so the client sees a result, not a transport error.
4. Set `readOnly` and `destructive` accurately. Clients use them to decide what needs user approval.
5. Add a test in `tests/Server.Tests` and, if it involves the router, `tests/Integration.Tests`.

See [`rhino/plugin/README.md`](rhino/plugin/README.md) for more.

## Reporting bugs

Open a [GitHub issue](https://github.com/mcneel/RhinoAI/issues) with:

- Rhino version and build (`SystemInfo` in Rhino)
- OS and architecture
- MCP client and version
- Output of `MCPStatus`
- Steps to reproduce, and the model or definition if one is involved
